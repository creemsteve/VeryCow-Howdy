# Voice implementation

VCH uses the 16 kHz DAC model, release `0.0.5`, exported into a shared pair of ONNX graphs. Desktop Java and Android use ONNX Runtime locally. Models are bundled in client releases. Microphone audio is never sent to a codec service or stored in the chat vault.

The implementation removes weight-normalization wrappers at export, removes training-loss computation from the encoding graph, reuses inference sessions, enables graph optimizations, bounds CPU worker threads and packs each 1,024-entry codebook index into 10 bits. There are 12 codebooks and a 320-sample hop, giving selectable token rates from 500 to 6,000 bits/s. These are codec token rates, not total network bandwidth. Signed JSON envelopes, AES-GCM, base64, HTTPS/TLS and polling add substantial overhead.

Audio is captured as mono PCM, reduced to 16 kHz, processed in roughly 0.5-second blocks, encoded, compressed/encrypted and signed by Java. Desktop and Android send one encrypted copy to the authenticated `/api/voice` HTTPS relay. Participants poll that server about every 800 ms for membership, speaking leases and new frames. Receivers verify the ML-DSA signature, channel binding, current key revision, author, speaking floor, timestamp and replay window before decrypting and decoding. The server handles authentication, channel access, floor leases, channel-key delivery and media relay. Audio processing stays local, but the server holds channel keys and could decrypt relayed media. Normal relay operation does not decrypt frames.

The server accepts media only from a joined participant holding the current speaking lease. It validates signed sender/server/channel bindings, voice kind, timestamp, ciphertext/signature size and key revision. Each channel keeps at most six live frames for at most three seconds in memory. Polling uses a live cursor, skips the sender's own frames, rejects obsolete key revisions and does not deliver earlier buffered audio to new participants. Slow receivers skip old blocks. Leaving, changing channels, access revocation, password changes and server shutdown clear the relevant live state. Audio is never appended to chat history or saved in the server vault.

At most one compliant participant can hold the speaking lease. Holding push-to-talk claims and renews the lease. Release, focus loss or leaving mutes processing. Leaving closes connections and stops microphone tracks. The receiver applies output gain before playback. There is a bounded send buffer; overloaded encoders drop blocks rather than accumulating an unbounded latency queue.

Desktop voice runs inside the Swing conversation window. Java Sound opens the selected microphone and playback device as 16 kHz mono PCM; the microphone line stays stopped until PTT acquires the floor. Java performs DAC encoding/decoding, gain, signing and encryption, and the existing pinned HTTPS client transports the same encrypted envelopes as Android. Desktop audio does not need a browser. Optional video opens a token-protected loopback browser panel sharing the existing voice session. Controls remain visible while browsing text channels. Mouse/keyboard release and window focus loss stop capture immediately; text entry does not activate keyboard PTT. Startup, relay requests and inference run outside the Swing event thread. Audio queues are bounded, and leaving closes devices and connections even during startup. Rejoining waits for the old session to leave before starting the new one. Desktop device preferences are applied when joining; reopen voice after changing them. Client-side channel-key handling and identity signing stay in Java, while the server supplies channel keys after password login. Android uses the bundled page inside a restricted WebView with a Java interface. Navigation, file access, content access and disk page caching are disabled; only the controlled local page receives the interface.

Both friend calls and community voice channels are hosted by the chat server. Clients never create peer media connections or exchange participant IP addresses. No ICE/STUN/TURN configuration or separate media port is needed; the existing HTTPS port is sufficient. In Tor-only mode every call and media request uses the saved local SOCKS5 route with remote hostname resolution and no direct retry. Tor must be running separately. Update both server and clients; the client requires `https-relay-v1` and the server rejects legacy peer signaling. Maximum voice membership defaults to 16 and is configurable up to 32.

This is block-based interactive voice rather than a proven low-latency streaming redesign of the DAC model. Expect at least the capture-block delay plus inference/network/polling/playback delay. Tor circuits add latency; stalled requests can exceed the speaking lease and interrupt a call. Reliable HTTPS/TCP delivery may also cause head-of-line delays, so bounded buffers drop late audio instead of preserving a complete recording. Short blocks can have audible boundaries because the neural model is not statefully streamed across them. On the build host, warmed 0.5-second sine-wave blocks encoded and decoded in approximately 135–145 ms; the first block took about 415–490 ms. These are local functional measurements, not comparative benchmarks or guarantees for Sonim hardware.

The loopback `VoiceBridge` serves the desktop video companion and the Android-compatible test fixture. Closing a video companion does not leave desktop audio; leaving desktop voice closes its bridge and removes all its video streams. Its requests require a per-session token and exact loopback Host/Origin checks, and no CORS access is granted.

Verification uses synthetic audio: desktop-to-desktop playback with one participant routed through a local SOCKS5 fixture, desktop/Android-compatible panel interoperability in both directions, floor exclusion/transfer, immediate release and cancelled late claims, audio-device cleanup and leave during startup. Protocol tests cover call initiation/acceptance and bidirectional encrypted media through SOCKS, proxy failure with no direct fallback, membership/access checks, forged and stale frames, key revisions, cursor delivery, bounded buffers, expiry and channel changes. Codec tests check 8,000, 8,320 and 16,000 samples, finite non-silent output, exact requested lengths and malformed packet rejection. Run `scripts/test.ps1` and, with Playwright available, `python scripts/test-voice-interop.py`. Real microphones, speaker hardware, acoustic quality, public Tor circuits, mobile WebView execution and Sonim latency require separate environment testing.

Upstream model and API reference: [DAC repository](https://github.com/descriptinc/descript-audio-codec). ONNX Runtime: [Java inference documentation](https://onnxruntime.ai/docs/get-started/with-java.html).

## Screen sharing and webcams

Community voice channels and two-person friend calls use the same optional video path. Desktop **Video / screen share** opens a browser companion while Swing keeps audio/PTT connected. Android embeds the controls in its voice panel. A participant may publish one screen and one webcam simultaneously. Starting either source requires an explicit click and the platform capture permission. Each source has an independent 50–1,000 kbps setting, changeable during a call. Receivers discover stream metadata first; each **Receive** checkbox starts unchecked. Only subscribed stream IDs are sent in subsequent polls. Unchecking also clears the canvas and closes the decoder; already in-flight responses are ignored. This is a bandwidth preference, not an access restriction against other authorized channel members.

Desktop WebCodecs requests `prefer-hardware`, trying AVC baseline with Annex B headers and VP8, then the available platform encoder when the hardware preference cannot be supported. Hardware acceleration is a platform hint rather than a guarantee: a browser may use software. Android uses Camera2 and MediaProjection surfaces directly with a `MediaCodecInfo.isHardwareAccelerated()` AVC encoder. It reports an error if no suitable hardware encoder exists. Displaying video requires WebCodecs support in the browser/WebView. No codec library, peer transport, STUN or TURN service is added. API references: [WebCodecs](https://www.w3.org/TR/webcodecs/), [Android MediaCodecInfo](https://developer.android.com/reference/android/media/MediaCodecInfo), and [MediaProjection](https://developer.android.com/reference/android/media/projection/MediaProjection).

The initial desktop dimensions are 640×360 for webcam and 960×540 for screen sharing, letterboxed to preserve source aspect ratio, at up to eight frames/s. Android chooses a supported camera size near 640×480, up to 1280×720, and a 960×540 projection. Frames are independently decodable keyframes, allowing late subscriptions, frame drops and separate receive choices without waiting for a prior frame. This deliberately trades compression efficiency for bounded buffering and recovery; busy encoders, slow relays and low bitrate settings reduce the delivered frame rate. Browser or device encoder support can vary, particularly on older Sonim/WebView installations.

The server authenticates `/api/video`, requires current joined voice membership and channel view/connect permission, and binds each published stream to its owner, channel and source. Video does not require the PTT speaking floor. Start/configure requests above 1,000 kbps or below 50 kbps are rejected. The encoder targets a lower rate to leave headroom; the sender drops frames that do not fit a conservative one-second budget. Independently, the server enforces a strict rolling one-second encrypted-payload budget of `kbps × 125` bytes for each stream, including across bitrate changes. Signed JSON envelope, base64, polling and TLS overhead are additional network traffic; the setting is not a total socket-bandwidth guarantee. Excess uploads receive HTTP 429 instead of accumulating a backlog. A malicious client cannot increase its accepted stream budget by declaring a higher bitrate.

Each video frame uses the existing compressed AES-256-GCM/ML-DSA envelope with `video/<stream UUID>` in the signed content kind. The encrypted payload is a four-byte big-endian JSON-header length, a UTF-8 header (`codec`, `width`, `height`, `timestamp`), and encoded keyframe bytes. The server validates ownership, signature, server/channel/stream binding, current key revision, size and freshness. The client checks these bindings again, verifies/decrypts, bounds decompression to 125,000 bytes, rejects replay IDs and validates decoder dimensions/codecs. Video queues hold at most 12 frames per stream for at most 1.5 seconds, with ten-second publication expiry unless media or the publisher's video poll refreshes it. Stop, leave, channel changes, permission revocation, bans, password changes and shutdown revoke the relevant streams. Video is never appended to chat history or vault snapshots. Server operators hold channel keys as they do for voice.

On Android, screen sharing starts a media-projection foreground service after system consent, with a persistent **Stop sharing** notification. While sharing another app, native heartbeats maintain membership and publication if WebView timers are suspended. Webcam capture stops when the voice activity backgrounds. Screen-off, call exit, activity destruction or stopping projection closes capture and the service. Calls without a screen share retain the existing background auto-lock behavior. Camera permission is requested separately and denial leaves audio available. Codec/network work uses bounded queues so network uploads do not block capture-device release.

Run `scripts/test.ps1` for relay membership, ownership, signature/replay checks, stream isolation, live configuration, subscription filtering, per-source rolling budgets, key rotation, expiry/cleanup and Tor routing. Run `python scripts/test-video.py` with Playwright installed for synthetic webcam/screen encode–encrypt–relay–decrypt–render checks, simultaneous streams, live bitrate changes, receive toggles and capture cleanup. These tests exercise real browser codecs, but they do not prove physical GPU selection or Android hardware capture. Physical camera/screen permission flows, Android foreground behavior, hardware encoder quality and public Tor video latency still require platform testing.
