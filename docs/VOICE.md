# Voice implementation

VCH uses the 16 kHz DAC model, release `0.0.5`, exported into a shared pair of ONNX graphs. Desktop Java and Android use ONNX Runtime locally. Models are bundled in client releases. Microphone audio is never sent to a codec service or stored in the chat vault.

The implementation removes weight-normalization wrappers at export, removes training-loss computation from the encoding graph, reuses inference sessions, enables graph optimizations, bounds CPU worker threads and packs each 1,024-entry codebook index into 10 bits. There are 12 codebooks and a 320-sample hop, giving selectable token rates from 500 to 6,000 bits/s. These are codec token rates, not total network bandwidth. Signed JSON envelopes, AES-GCM, base64, DTLS/SCTP and ICE add substantial overhead.

Audio is captured as mono PCM, reduced to 16 kHz, processed in roughly 0.5-second blocks, encoded, compressed/encrypted and signed by Java. Desktop native WebRTC (webrtc-java) and the Android embedded panel send ciphertext over unordered, non-retransmitting WebRTC data channels. Receivers verify the ML-DSA signature, channel binding, current key revision, author, speaking floor, timestamp and replay window before decrypting and decoding. WebRTC transports DAC tokens as application data; no unsupported SDP audio-codec negotiation is claimed. The server handles authentication, channel access, floor leases, channel-key delivery and ICE/SDP signaling. Audio processing and normal media transport stay on the clients, but the server holds channel keys and could decrypt captured media.

At most one compliant participant can hold the speaking lease. Holding push-to-talk claims and renews the lease. Release, focus loss or leaving mutes processing. Leaving closes connections and stops microphone tracks. The receiver applies output gain before playback. There is a bounded send buffer; overloaded encoders drop blocks rather than accumulating an unbounded latency queue.

Desktop voice runs inside the Swing conversation window. Java Sound opens the selected microphone and playback device as 16 kHz mono PCM; the microphone line stays stopped until PTT acquires the floor. Java performs DAC encoding/decoding, gain, signing and encryption, and the bundled native WebRTC library transports the same data-channel envelopes as Android. No browser, local HTTP listener or web page is used by the desktop client. Controls remain visible while browsing text channels. Mouse/keyboard release and window focus loss stop capture immediately; text entry does not activate keyboard PTT. Startup, signaling and inference run outside the Swing event thread. Audio queues are bounded, and leaving closes devices and connections even during startup. Rejoining waits for the old session to leave before starting the new one. Desktop device preferences are applied when joining; reopen voice after changing them. Native WebRTC uses a headless audio module so it never captures a second microphone or creates standard audio tracks. Client-side channel-key handling and identity signing stay in Java, while the server supplies channel keys after password login. Android uses the bundled page inside a restricted WebView with a Java interface. Navigation, file access, content access and disk page caching are disabled; only the controlled local page receives the interface.

Configure ICE URLs in Audio for internet connections. On one LAN, host candidates often suffice. There are no default public STUN services. The current UI accepts STUN URLs and TURN URLs without credentials; authenticated TURN configuration is not implemented. Restrictive NATs may need an additional authenticated TURN configuration feature before connections work reliably. Peer-to-peer voice can reveal participant IP addresses to other channel members. Each sender sends one copy per peer; maximum voice membership defaults to 16 and is configurable up to 32.

This is block-based interactive voice rather than a proven low-latency streaming redesign of the DAC model. Expect at least the capture-block delay plus inference/network/playback delay. Short blocks can have audible boundaries because the neural model is not statefully streamed across them. On the build host, warmed 0.5-second sine-wave blocks encoded and decoded in approximately 135–145 ms; the first block took about 415–490 ms. These are local functional measurements, not comparative benchmarks or guarantees for Sonim hardware.

The loopback `VoiceBridge` remains only as a test fixture for the Android-compatible page; the desktop client does not instantiate it. Its requests require a per-session token and exact loopback Host/Origin checks, and no CORS access is granted.

Verified: two native Windows peers using synthetic microphone PCM, signed encrypted DAC playback, floor exclusion/transfer, immediate release and cancelled late claims, audio-device cleanup and leave during startup; Java encode/decode at 8,000, 8,320 and 16,000 samples; finite non-silent output and exact requested output lengths; malformed DAC packet rejection; two browser peers connected with synthetic microphones; remote signed encrypted DAC playback scheduling; second speaker denied; floor transfer; microphone-track cleanup on leaving. The `scripts/test-voice-interop.py` test checks the native desktop and Android-compatible panel in both directions with synthetic audio. Real microphones, speaker hardware, acoustic quality, WAN connections, mobile WebView execution and Sonim latency have not been verified here.

Upstream model and API reference: [DAC repository](https://github.com/descriptinc/descript-audio-codec). ONNX Runtime: [Java inference documentation](https://onnxruntime.ai/docs/get-started/with-java.html).
